# Безопасность и приватность

> Платформа хранит контакты, переписку и фото людей. Принцип — **собирать минимум, показывать только по явному
> действию, ничего не делать скрытно**. Юридические формулировки (сроки, тексты согласий) утверждает юрист,
> здесь — инженерная реализация.

## 1. Модель угроз (STRIDE)

| Угроза | Пример | Контрмеры |
|---|---|---|
| Подмена личности | Перебор OTP, SIM-swap, кража refresh-токена | Лимиты и блокировки OTP, короткий access-токен, ротация refresh с обнаружением повторного использования, MFA для персонала |
| Изменение данных | Мастер правит чужую заявку, подмена цены | Проверка владения в каждом сервисе, а не только на шлюзе; аудит изменений |
| Отказ от действий | «Я не раскрывал контакты», «модератор не скрывал отзыв» | Журналы только на добавление: раскрытия, решения модерации, действия админов |
| Утечка данных | Парсинг контактов, утечка дампа, ПДн в логах | Лимиты раскрытия, шифрование ПДн на уровне приложения, очистка логов и трейсов |
| Отказ в обслуживании | Флуд поиска, OTP-бомбинг | WAF и ARL, GCRA-лимиты, load shedding, капча по риску |
| Повышение привилегий | Клиент вызывает админский маршрут | RBAC на шлюзе по реестру маршрутов + проверка роли в сервисе, отдельный хост и MFA для админки |

## 2. 152-ФЗ

- **Локализация.** Все ПДн хранятся и обрабатываются в РФ (Yandex Cloud, `ru-central1`). Сторонних трекеров,
  пикселей и аналитических SDK, передающих данные за рубеж, нет.
- **Оператор ПДн.** Уведомление в Роскомнадзор, политика обработки ПДн опубликована. Согласие на обработку
  оформляется отдельно от пользовательского соглашения. Согласия на аналитику и маркетинг — отдельные и
  необязательные.
- **Инциденты.** Утечку ПДн уведомляем в РКН в течение 24 часов (первичное уведомление) и 72 часов (результаты
  расследования). Процедура — в §11.
- **Меры защиты** соответствуют уровню защищённости информационной системы ПДн (модель угроз и акт
  классификации ведутся как документы).

## 3. Классификация данных

| Класс | Примеры | Правила |
|---|---|---|
| Публичные | Профиль мастера, цены, опубликованные отзывы | Кэшируются на CDN, индексируются |
| Внутренние | Агрегаты, метрики, логи без ПДн | Доступ сотрудникам по роли |
| Конфиденциальные ПДн | Телефон, email, имя клиента, текст заявки, переписка, фото заявок | Шифрование на уровне приложения (телефон, email), доступ только сервису-владельцу, маскирование в логах |
| Особо защищаемые | Документы верификации мастера, секреты аутентификации | Отдельный бакет с KMS, доступ модераторам через короткие presigned-ссылки, удаление после проверки |

## 4. Минимизация и контроль контактов

- **Поиск, сравнение и просмотр профилей — без регистрации.** Аккаунт нужен только для заявок, чата, синхронизации
  избранного и кабинета мастера. Избранное и сравнение работают локально и переносятся в аккаунт после входа.
- **Телефон клиента скрыт по умолчанию.** Мастер видит его, только если клиент включил «поделиться телефоном»
  (`sharePhone`). Иначе общение идёт во встроенном чате.
- **Мастер сам выбирает политику контактов:** показывать всем, только после заявки или только чат.
- **Раскрытие контактов логируется и ограничено:** лимит в сутки на пользователя и в час на IP. При аномалиях
  включается невидимая капча. Мастер видит, сколько раз открывали его контакты.
- **Автоматическое маскирование.** Телефоны и email в тексте заявки скрываются, если пользователь не разрешил их
  показывать.
- **Урезание IP.** В журналах хранится до /24 (IPv4) и /48 (IPv6). User-Agent сводится к семейству браузера и ОС.
- **Аналитика только при согласии** (`POST /v1/events` без согласия не вызывается). Идентификатор в аналитике
  псевдонимный (`user_hash` = HMAC с секретом), сырых ПДн в ClickHouse нет.

## 5. Шифрование

- **В пути.** TLS 1.2+ (предпочтительно 1.3) на балансировщике (Certificate Manager), HSTS с preload. Внутри
  кластера — прозрачное шифрование трафика между подами (Cilium WireGuard). Подключения к managed-хранилищам —
  только TLS с проверкой сертификата (`sslmode=verify-full`, `rediss://`).
- **В покое.** Диски managed-хранилищ и узлов шифруются. Object Storage — SSE с ключом KMS (ротация ежегодно).
  Секреты Kubernetes в etcd шифруются ключом KMS.
- **На уровне приложения.** Телефон, email и Telegram шифруются AES-256-GCM (`FieldCipher` в `@masterly/platform`),
  ключ приходит из Lockbox; в production сервис не стартует с ключом разработки. Для поиска и дедупликации есть
  детерминированный HMAC-SHA256. Дамп БД без ключа контактов не раскрывает. Этап 2 — конвертная схема: ключ
  данных обёрнут ключом KMS и кэшируется в памяти.

## 6. Аутентификация и сессии

- **Вход по одноразовому коду** (SMS или email).
  - Код из 6 цифр живёт 5 минут, на ввод 5 попыток.
  - Повторная отправка — не чаще раза в 60 секунд.
  - Лимиты действуют на номер, IP и подсеть.
  - Защита от SMS-pumping: дневной лимит отправок на направление и контроль конверсии код → вход по оператору.
- **Access-токен — JWT на EdDSA (Ed25519), живёт 15 минут.** Шлюз проверяет его локально по JWKS (`kid`).
  Ключи ротируются раз в 30 дней с перекрытием: JWKS публикует старый и новый ключ.
- **Refresh-токен — случайные 256 бит,** в БД хранится только хэш. Токен меняется при каждом использовании.
  Предъявление уже использованного токена отзывает всё семейство сессий (признак кражи).
- **Cookie** `__Host-` с флагами `HttpOnly; Secure; SameSite=Lax`. Refresh-cookie ограничена путём обновления.
  Токены никогда не попадают в `localStorage`.
- **CSRF.** Изменяющие запросы с cookie-аутентификацией дополнительно проверяют `Origin`.
- **Персонал** (модераторы, администраторы) входит только с вторым фактором (TOTP или passkey), сессия до
  8 часов. Админка доступна на отдельном хосте. Для клиентов passkeys появятся на этапе 2.

## 7. Авторизация

- **Роли:** `client`, `master`, `master_staff` (сотрудник филиала), `moderator`, `admin`, `support`.
- **Два рубежа.**
  1. Шлюз проверяет уровень доступа маршрута из реестра контрактов (`public`, `user`, `master`, `admin`).
  2. Сервис проверяет владение ресурсом: мастер видит только свои заявки, сотрудник — только заявки своего
     филиала, клиент — только свои диалоги.
  Ошибка в одном рубеже не открывает данные.
- **Межсервисные вызовы.** Внутри кластера сервисы получают личность пользователя в метаданных gRPC от шлюза.
  NetworkPolicy разрешает только вызовы из графа зависимостей ([`values/*.yaml`](../../infra/helm/values)),
  по умолчанию всё запрещено (default-deny).
- **Действия персонала** (скрыть отзыв, заблокировать профиль, просмотр ПДн в поддержке) пишутся в аудит с
  указанием причины.

## 8. Права субъекта ПДн

| Право | Реализация |
|---|---|
| Доступ и экспорт | `POST /v1/me/export` → шлюз синхронно собирает данные из сервисов-владельцев через gRPC (профиль, настройки и журнал согласий — identity, заявки — leads, отзывы — reviews, избранное) и отдаёт JSON `masterly.personal-data.v1`; не больше 3 выгрузок в сутки. Фоновая сборка архива в Object Storage — когда объём данных пользователя перестанет укладываться в бюджет запроса |
| Удаление аккаунта | identity деактивирует аккаунт и публикует `AccountDeletionRequested` в `identity.account.v1`. Каждый сервис сразу удаляет публичные ПДн, остальное обезличивает, а данные под обязательным хранением удаляет после `retain_until` |
| Управление согласиями | Настройки в профиле. Каждое изменение пишется в журнал согласий и публикуется `ConsentChanged`. analytics перестаёт принимать события и удаляет накопленные по `user_hash` |
| Отзыв согласия | Так же просто, как дать: один переключатель, без «тёмных паттернов» |

Удаление проверяется контрактным тестом: после события ни один сервис не возвращает ПДн пользователя.
Из компактированных топиков данные исчезают по tombstone не позже чем через 7 дней ([events.md](events.md#типы-событий-и-снимки)).

## 9. Защита API и антиспам

- **Периметр.** WAF (Smart Web Security: правила OWASP, лимиты ARL) и защита от DDoS на балансировщике.
- **Валидация.** На шлюзе — zod-схемы из контрактов (лишние поля отбрасываются), внутри — типы protobuf.
  Размеры тел ограничены на каждом маршруте.
- **Браузер.** CSP с nonce, `frame-ancestors 'none'`, `X-Content-Type-Options`, `Referrer-Policy`,
  `Permissions-Policy` (уже в [`next.config.ts`](../../apps/web/next.config.ts)).
- **Загрузки.**
  - Только через presigned PUT с ограничением типа и размера.
  - Сервер проверяет сигнатуру файла (magic bytes), а не расширение.
  - EXIF с геопозицией удаляется до публикации.
  - Сервер никогда не скачивает файлы по ссылке пользователя, поэтому SSRF исключён.
- **Спам в чате и заявках.**
  - Лимиты частоты.
  - SimHash повторяющихся сообщений в разных диалогах.
  - Ссылки и телефоны в первом сообщении от нового аккаунта уходят на проверку.
  - Кнопки «пожаловаться» и «заблокировать».
- **Фейковые отзывы и дубликаты профилей** — сервис trust. Отзыв возможен только по завершённой заявке. Скорость
  и кластеры отзывов (устройства, подсети, похожесть текстов) дают оценку риска. Дубликаты профилей находятся по
  совпадению полос SimHash описания, хэшей телефонов и pHash фотографий.

## 10. Цепочка поставки и платформа

- **Зависимости.** Lock-файл, `minimumReleaseAge` (свежие версии ставятся после выдержки), скрипты установки
  запрещены по умолчанию (`allowBuilds`), обновления — через Renovate с ревью.
- **Сборка.**
  - SBOM и provenance (SLSA) для каждого образа.
  - Подпись cosign (keyless, OIDC GitHub).
  - Сканирование Trivy, CodeQL, поиск секретов в репозитории.
- **Кластер принимает только подписанные образы** из своего реестра (политика проверки подписи на admission).
- **Образы distroless,** процесс от непривилегированного пользователя, корневая ФС только для чтения,
  `seccompProfile: RuntimeDefault`, Pod Security Admission `restricted`.
- **Секреты** хранятся в Lockbox, в поды попадают через External Secrets Operator. В репозитории и образах
  секретов нет. CI получает доступ к облаку через федерацию OIDC, без статических ключей.

## 11. Аудит и инциденты

- **Аудит.** Журнал только на добавление: вход персонала, решения модерации, просмотр ПДн поддержкой, раскрытия
  контактов, экспорт и удаление данных, смена ролей. Хранится год, копия уходит в отдельное хранилище, доступное
  только службе безопасности.
- **Реагирование.**
  1. Обнаружение (алерты, аномалии в аудите).
  2. Оценка затронутых данных и сдерживание (ротация ключей, отзыв сессий).
  3. Уведомление РКН в течение 24 и 72 часов, уведомление пользователей.
  4. Разбор без поиска виноватых.

## 12. Платежи и реклама

- **Платёжных данных нет совсем** ([ADR-0009](../adr/0009-no-payments.md)): ни форм оплаты, ни SDK
  платёжных провайдеров, ни хранения реквизитов карт. Платные функции оплачиваются по счёту, который выставляет
  бухгалтерия. Платформа хранит только статус тарифа. Требования PCI DSS к нам не применимы.
- **Реклама маркируется.** Продвигаемые карточки показываются в отдельных слотах с пометкой «Реклама», указанием
  рекламодателя и токеном erid. Данные о показах передаются в ОРД. Скрытого влияния рекламы на органическое
  ранжирование нет.
