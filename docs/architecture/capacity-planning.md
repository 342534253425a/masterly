# Планирование мощностей

> Цель: выдержать треть нагрузки крупнейшего классифайда РФ и остаться в SLO при отказе одной зоны.
> Цифры ниже — **инженерная модель до первых замеров**. Её проверяет k6 ([`tests/load`](../../tests/load)),
> после каждого прогона таблицы уточняются.

## 1. От аудитории к RPS

Внутренних метрик Avito у нас нет. Берём публичный порядок величины — около 70 млн пользователей в месяц — и строим
модель от трети этой аудитории.

| Параметр | Значение | Комментарий |
|---|---|---|
| MAU | 25 млн | ⅓ аудитории ориентира |
| DAU | 8 млн | DAU/MAU ≈ 32 % |
| Сессий в сутки | 17,6 млн | 2,2 сессии на активного пользователя |
| API-вызовов на сессию | 36 | Поиск, подсказки, профили, карта, справочники, сессия, чат, события |
| API-вызовов в сутки | 634 млн | 17,6 млн × 36 |
| Средний RPS | 7 300 | 634 млн / 86 400 |
| Пиковый коэффициент | × 3 | Вечерний пик 19–22 МСК; все города MVP живут по московскому времени |
| Запас на кампании и сезонность | × 1,15 | |
| **Проектный пик на шлюзе** | **25 000 RPS** | 7 300 × 3 × 1,15 |

Страницы Next.js считаются отдельно: 17,6 млн сессий × 6 просмотров дают ~3 700 страниц/с в пике. Около 20 % из
них — SEO-страницы, которые отдаёт CDN (ISR). Остаётся **~3 000 динамических рендеров/с**. Их запросы к API уже
входят в 25 000 RPS.

## 2. Профиль трафика шлюза в пике

| Группа | Доля | Пик, RPS | Что происходит за шлюзом |
|---|---|---|---|
| Поиск `GET /v1/search` | 36 % | 9 000 | search → Redis (кэш выдачи, ~40 % попаданий) → OpenSearch → гидратация карточек |
| Подсказки `GET /v1/search/suggest` | 20 % | 5 000 | search → Redis (популярные префиксы, ~80 %) → OpenSearch |
| Профиль, цены, отзывы | 16 % | 4 000 | catalog (Redis read-through, реплики PG), reviews |
| Карта `GET /v1/search/map` | 8 % | 2 000 | search → кэш по тайлу (~60 %) → гео-агрегации OpenSearch |
| Справочники и SEO (промахи CDN) | 6 % | 1 500 | catalog, кэш на шлюзе |
| Сессия и профиль пользователя | 6 % | 1 500 | JWT проверяется на шлюзе локально, identity — только refresh и профиль |
| Сообщения (REST) | 4 % | 1 000 | messaging; живые сообщения идут по WebSocket |
| Продуктовые события (батчи) | 2 % | 500 | шлюз → Kafka `analytics.events.v1`, до 50 событий в запросе |
| Запись: заявки, ответы, отзывы, избранное, контакты | 2 % | 500 | leads / reviews / messaging: транзакция + outbox |

Смесь в [`tests/load/search.js`](../../tests/load/search.js) повторяет пропорции чтения: 55 % поиск, 20 % подсказки,
15 % профиль, 10 % карта. [`tests/load/lead-flow.js`](../../tests/load/lead-flow.js) проверяет путь записи.

## 4. Вычисления (Kubernetes)

Формула: `подов = пиковая нагрузка × CPU на операцию / (запрос CPU пода × 0,65)`. Здесь 0,65 — целевая загрузка HPA.
Лимиты CPU не ставим: это исключает CFS-троттлинг, ограничена только память. Поды могут временно потреблять больше
запрошенного, и именно это поглощает пик до реакции автоскейлера.

| Сервис | Пиковая нагрузка | CPU на операцию* | vCPU в пике | Запрос пода | Подов в пике | min / max (Helm) |
|---|---|---|---|---|---|---|
| gateway | 25 000 RPS | 0,8 мс | 20 | 0,5 | ~62 | 6 / 80 |
| web | 3 000 рендеров/с | 8 мс | 24 | 1 | ~37 | 6 / 60 |
| search | 16 000 RPC (поиск 9k, подсказки 5k, карта 2k) | ~1,06 мс | 17 | 1 | ~26 | 6 / 60 |
| catalog | ~6 000 RPC (профили, гидратация, кабинет) | 0,5 мс | 3 | 0,25 | ~19 | 4 / 24 |
| identity | ~1 500 RPC | 0,6 мс | 0,9 | 0,25 | ~6 | 3 / 12 |
| leads | ~1 500 RPC чтения + ~50 TPS записи | 1 мс | 1,5 | 0,5 | ~5 | 4 / 30 |
| reviews | ~800 RPC | 0,8 мс | 0,6 | 0,25 | ~4 | 3 / 16 |
| messaging | 150 тыс. WS + 1 000 RPS | ограничение по памяти: ~5 000 соединений на под | — | 0,5 / 512 Mi | ~30 | 4 / 40 |
| analytics | 17 000 событий/с из Kafka | 0,05 мс | ~1 | 0,5 | по лагу (KEDA) | 3 / 48 |
| notifications, media, trust | сотни событий/с | — | < 1 | 0,25 | минимум | 2–3 / 12–24 |

\* Оценки CPU: проверка JWT EdDSA ≈ 0,1 мс, GCRA в Redis — один RTT, protobuf → JSON для выдачи 10–20 КБ ≈ 0,3–0,5 мс.
Карточки в кэше хранятся в protobuf, поэтому catalog отдаёт их без пересборки объекта.

**Узлы.** В пике сумма запросов около 125 vCPU. Пул `apps` состоит из узлов по 16 vCPU / 64 ГБ, минимум 4 узла
в каждой из трёх зон, всего 12 узлов и ~186 vCPU allocatable. Значит, пик помещается без ожидания автоскейлера
при упаковке ~67 %. При потере зоны в оставшихся 8 узлах ~124 vCPU — впритык к пику. Поды временно работают
горячее (запас HPA 35 %), а Cluster Autoscaler за несколько минут добавляет узлы в живых зонах (до 30 на зону).
Потребители Kafka работают в отдельном пуле `consumers` с taint, чтобы пакетная обработка не отнимала CPU у онлайн-пути.

## 5. Хранилища

### PostgreSQL

| Кластер | Пресет × хосты | Нагрузка в пике | Объём | Почему такой размер |
|---|---|---|---|---|
| catalog | s3-c16-m64 × 3 | < 2 000 QPS чтения на реплики (промахи кэша), < 100 TPS записи | ~100 ГБ: 1,5 млн мастеров, ~150 млн цен | Рабочий набор (~30 ГБ) целиком в памяти |
| leads | s3-c16-m64 × 3 | ~1 500 QPS чтения, ~50 TPS записи | ~300 ГБ/год с индексами | Рост истории; секции по месяцам |
| messaging | s3-c16-m64 × 3 | ~1 000 QPS чтения, ~300 TPS записи | ~1 ТБ/год | Самый быстрорастущий объём |
| core | s3-c8-m32 × 3 | identity, reviews, notifications, media, trust | < 200 ГБ | Лёгкие домены: отдельные БД и пользователи в общем кластере |

- **Соединения.** Пулер Odyssey работает в transaction mode. Каждый под держит пул на 8 соединений. Пик для
  messaging: 40 подов × 8 = 320 клиентских соединений, при этом серверных соединений к PG гораздо меньше
  `max_connections = 800`.
- **Запас.** PostgreSQL здесь не узкое место по CPU. Пресеты выбраны под объём данных и рабочий набор в памяти.
  На старте можно взять ступень ниже: вертикальное масштабирование managed-PG — это переключение мастера,
  запись недоступна несколько секунд.

### OpenSearch

- 1,5 млн документов-мастеров. Цены вложены как `nested` (8–14 услуг на мастера, по 5 сегментов устройств в
  `tier_prices`), это ~20 млн вложенных документов и ~15 ГБ первичных данных.
- Индекс `masters-vN`: 12 первичных шардов и 2 реплики, то есть каждый шард есть во всех трёх зонах
  (allocation awareness). Routing идёт по `city_id` с `routing_partition_size = 3`. Запрос попадает в 3 шарда
  вместо 12, а Москва не превращается в один горячий шард.
- Нагрузка: после кэшей до OpenSearch доходит ~7 200 запросов/с. Это ~21 600 шард-запросов/с при ~2 мс CPU на
  каждый, то есть ~43 vCPU из 144 на 9 узлах. Загрузка CPU ≈ 30 %, при потере зоны ≈ 45 %. Индекс целиком
  помещается в page cache (9 × 64 ГБ).

### Valkey / Redis

| Использование | ops/с в пике | Память |
|---|---|---|
| Rate limiting (GCRA, один Lua-вызов на запрос) | 25 000 | ~0,1 ГБ |
| Кэш выдачи и подсказок | 19 000 | ~4 ГБ (TTL 60 с) |
| Карточки мастеров (MGET при гидратации) | 13 000 | ~6 ГБ |
| Сессии, OTP, идемпотентность | 2 500 | ~0,5 ГБ |
| Rate limit сообщений, счётчики непрочитанного, pub/sub чата (этап 1.1) | 1 500 | ~0,5 ГБ |
| **Итого** | **~61 000** | **~11 ГБ** |

6 шардов × 16 ГБ, у каждого шарда реплика в другой зоне. Это около 10 тыс. ops/с на шард (единицы процентов
возможностей) и пятикратный запас памяти. Шардов много не из-за нагрузки: так горячие ключи распределяются по
слотам, а failover одного шарда затрагивает только ⅙ ключей.

### Kafka

- Входящий поток в пике ~18 000 сообщений/с (~12 МБ/с до сжатия): `analytics.search.v1` 9 000/с,
  `analytics.events.v1` 7 500/с, доменные события ~1 000/с. С RF = 3 — около 36 МБ/с записи на кластер из
  6 брокеров. Загрузка < 15 %.
- Диск: аналитические топики за 3 дня после zstd и репликации занимают ~0,8 ТБ из 6 ТБ. Хватает на продление
  retention до 7 дней для переигрывания.
- Партиций с запасом ×10: смена числа партиций у ключевого топика ломает соответствие ключ → партиция, а значит
  и порядок. Всего 400+ партиций × RF 3 ≈ 210 реплик на брокер — далеко от лимитов.

### ClickHouse

- Вставка ~17 000 строк/с в пике батчами ≥ 10 000 строк или раз в 1–2 с на шард.
- Сырые события: ~9,5 ГБ/сутки после сжатия, хранятся 180 дней. Поиски с показами (`shown_ids`): ~34 ГБ/сутки,
  90 дней. Агрегаты (`master_daily`, `search_gaps_daily`) хранятся бессрочно.
- Горячие 30 дней (~1,3 ТБ, ~0,45 ТБ на шард) лежат на локальных SSD. Более старые партиции по TTL уезжают на
  диск в Object Storage (~4 ТБ).

### Object Storage

Портфолио: 1,5 млн мастеров × ~30 фото × ~400 КБ ≈ 18 ТБ, отдаётся через CDN. Фото заявок и чатов — ~70 ГБ/сутки.
Они удаляются через год после закрытия заявки и сразу при удалении аккаунта.

## 6. Отказ зоны (N+1 по зонам)

- **Stateless.** `topologySpreadConstraints` по зонам и узлам, PDB `minAvailable: 66%`, HPA с целевой загрузкой
  65 %. Потеря трети подов поглощается запасом до прихода новых узлов.
- **PostgreSQL, Redis.** Автоматический failover на реплику в другой зоне.
- **Kafka.** RF = 3, `min.insync.replicas = 2`: запись переживает потерю зоны.
- **OpenSearch.** Копия каждого шарда есть в каждой зоне.
- **ClickHouse.** Аналитика может отставать. Потребитель ставит партиции на паузу, данные ждут в Kafka (3 дня).

## 7. Как подтверждаем

| Профиль k6 | Когда | Цель |
|---|---|---|
| `smoke` | После каждой выкладки (CD) | Всё отвечает, пороги SLO не нарушены |
| `load` | Еженедельно на staging; перед запуском — на боевой инфраструктуре до открытия трафика | Номинал в SLO |
| `stress` | Ежемесячно | Где ломаются p95 и доля ошибок, что сдаётся первым |
| `spike` | Перед кампаниями | ×5 за 30 с: реакция HPA/KEDA и load shedding |
| `soak` | Перед крупными релизами | 4 часа: утечки памяти, рост лага, деградация пулов |

```bash
k6 run tests/load/search.js -e PROFILE=load -e TARGET_RPS=2500 -e BASE_URL=https://staging.masterly.ru
```

Staging уменьшен примерно в 10 раз. Шаг масштабирования подов линейный, поэтому результаты экстраполируются на
прод по подам. Managed-хранилища один раз проверяются в полном размере: прогон на 25 000 RPS через распределённый
k6 (k6-operator) по боевому окружению до запуска пользователей.

## 8. Когда и что масштабировать дальше

| Сигнал | Действие |
|---|---|
| CPU реплик PG catalog > 60 % устойчиво | Ещё одна реплика; тяжёлые выборки кабинета — в ClickHouse |
| Запись в одном кластере PG > 5 000 TPS или объём > 2 ТБ | Шардирование приложением по `client_id` / `conversation_id` (карта шардов в конфиге) или распределённая СУБД |
| p95 OpenSearch > 150 мс | Больше data-узлов или реплик; отдельные индексы для крупнейших регионов |
| Память Redis > 70 % | Онлайн-решардинг (добавить шард) |
| Партиция > 5 МБ/с или лаг растёт при максимуме подов | Для аналитики — больше партиций; для ключевых топиков — новая версия `…v2` |
| Новые регионы РФ за пределами МСК | Пиковый коэффициент падает (часовые пояса), сначала пересчитать модель |
| Запись > 50 000 TPS суммарно | Переход на cell-архитектуру: независимые «ячейки» по группам городов |
