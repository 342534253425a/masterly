# Устойчивость

> Задача — не «никогда не падать», а **падать частично и предсказуемо**. Отказ любой одной зависимости
> ухудшает часть функций, но не останавливает платформу. Реализация — `@masterly/platform`
> (дедлайны, ретраи, circuit breaker на cockatiel, graceful shutdown).

## 1. Цели

| Показатель | Цель |
|---|---|
| Доступность API (не-5xx) | 99,95 % за 30 дней |
| Поиск p95 / p99 | 250 / 600 мс |
| Создание заявки p95 / p99 | 400 / 900 мс |
| Свежесть поиска после правки профиля | ≤ 30 с (p99) |
| Потеря подтверждённых записей при отказе зоны | 0 |
| RPO / RTO при порче данных | ≤ 5 мин / ≤ 1 ч на кластер |

Все цели — на [дашборде SLO](observability.md#5-slo-и-алерты). Расход бюджета ошибок определяет, что делаем:
выкатываем новое или чиним.

## 2. Модель отказов

| Что отказывает | Как часто | Защита |
|---|---|---|
| Под, узел | Ежедневно | Реплики в разных зонах и на разных узлах, PDB 66 %, ретраи на идемпотентных вызовах |
| Зона доступности | Редко, но бывает | Три зоны, запас HPA 35 %, синхронные реплики managed-хранилищ, Kafka RF 3 / min ISR 2 |
| Медленная зависимость | Еженедельно | Дедлайны, circuit breaker, bulkhead, load shedding |
| Плохой релиз | Ежемесячно | Канареечный выпуск, флаги функций, откат GitOps-коммитом, миграции expand/contract |
| Порча данных (ошибка кода или оператора) | Редко | PITR, журналы только на добавление, отложенное удаление |
| Регион целиком | Очень редко | Бэкапы вне региона, IaC для развёртывания с нуля (§10) |

## 3. Дедлайны и таймауты

У каждого запроса есть **бюджет времени**. Он назначается на шлюзе и уменьшается на каждом переходе. Если остатка
не хватает на осмысленную работу, сервис сразу отвечает `DEADLINE_EXCEEDED` и не тратит ресурсы впустую.

| Переход | Таймаут | Комментарий |
|---|---|---|
| ALB → gateway / web | idle 60 с | keep-alive на шлюзе 65 с: соединение закрывает балансировщик, а не сервер (иначе случайные 502) |
| Бюджет маршрута на шлюзе | поиск 800 мс, чтение 1,5 с, запись 2 с | Задан в реестре маршрутов; экспорт данных — асинхронно |
| Шлюз → сервис (gRPC) | остаток бюджета − 20 мс | Передаётся в `grpc-timeout`, сервис видит свой дедлайн |
| Сервис → сервис | min(остаток, собственный лимит вызова) | Дедлайн не удлиняется ниже по цепочке |
| Redis | 50 мс на команду | Кэш работает по принципу fail-open: ошибка = промах |
| PostgreSQL | `statement_timeout` 5 с; на пути пользователя — `SET LOCAL` по остатку дедлайна | `lock_timeout` 3 с |
| OpenSearch | 400 мс + `timeout` в теле запроса | Частичная выдача лучше пустой |
| Kafka (relay) | 10 с на батч, `acks=all` | Неудачный батч останется в outbox |
| Внешние провайдеры (SMS, email, push) | 3 с + circuit breaker | Только из асинхронных потребителей, не на пути запроса |

## 4. Повторы

- **Повторяются только идемпотентные операции:** чтения, gRPC-методы с пометкой идемпотентности и записи с
  `Idempotency-Key`.
- **Не больше одного повтора на пути пользователя.** Экспоненциальная задержка с полным jitter.
- **Бюджет повторов** — не больше 10 % запросов к цели за 10 с (token bucket). При массовом сбое повторы не
  удваивают нагрузку на и без того больную зависимость.
- **Что не повторяется:** `INVALID_ARGUMENT`, `PERMISSION_DENIED`, исчерпанный дедлайн, `RESOURCE_EXHAUSTED` без
  `Retry-After`.
- **Браузер.** TanStack Query повторяет запрос один раз с задержкой. Мутации без ключа идемпотентности не
  повторяются. Заявка, отправленная офлайн, ставится в очередь PWA (Background Sync) и уходит с тем же ключом.

## 5. Circuit breaker

Отдельный breaker на каждую цель вызова (`target`: сервис, OpenSearch, внешний провайдер):

- **Открывается** при ≥ 50 % ошибок за скользящие 10 с (минимум 20 вызовов) или после 5 ошибок подряд.
- **Полуоткрытое состояние** наступает через 10 с, при повторных срабатываниях интервал растёт до 60 с.
- **Пока открыт** — мгновенный fallback из матрицы деградации (§8), без ожидания таймаута.
- Состояние видно в метрике `circuit_breaker_open{target}` и на дашборде сервиса.

## 6. Изоляция (bulkhead)

- **Отдельные пулы на каждую зависимость:** gRPC-каналы, соединения PG, лимит параллельных вызовов. Медленный
  OpenSearch не съедает соединения, нужные для заявок.
- **Классы приоритета маршрутов на шлюзе:**
  - *critical* — вход, заявки, сообщения;
  - *normal* — поиск, профили;
  - *low* — подсказки, карта, продуктовые события.
  У каждого класса свой лимит параллельности.
- **Отдельные пулы узлов.** Потребители Kafka (`consumers`) работают отдельно от онлайн-сервисов (`apps`).
- **Тяжёлые операции мастеров** (импорт тысяч цен, выгрузка отчёта) выполняются асинхронными задачами с лимитом
  на мастера.
- **Отдельная БД у каждого сервиса** — тоже bulkhead: блокировки и VACUUM одного домена не задевают другие.

## 7. Перегрузка

- **Rate limiting.** GCRA в Redis по ключам «маршрут × пользователь / IP». Лимиты берутся из реестра контрактов
  (`rateLimit`). Ответ `429` с заголовками `RateLimit-*` и `Retry-After`. При недоступности Redis работает
  приблизительный локальный лимитер в каждом поде.
- **Адаптивный лимит параллельности на шлюзе** (градиентный алгоритм по задержке, как в Netflix concurrency-limits).
  Лишние запросы получают `503` с `Retry-After`, класс *low* отсекается первым.
- **Задержка event loop.** Если p99 задержки цикла событий Node.js > 100 мс, под отбрасывает низкоприоритетные
  запросы, пока не восстановится.
- **Обратное давление в потребителях.** При насыщении зависимости партиции ставятся на паузу, размер батча адаптивный.
- **Аварийные выключатели.** Флаги функций снимают дорогие возможности (кластеры на карте, подсказки,
  персонализацию) одним переключением.

## 8. Матрица деградации

| Отказала зависимость | Поведение | Что видит пользователь |
|---|---|---|
| OpenSearch | Выдача популярных запросов из кэша (до 1 ч устаревания); иначе упрощённый поиск в catalog (город + услуга, по рейтингу) под жёстким лимитом | Плашка «результаты могут быть неполными», карта без кластеров |
| Redis | Кэш обходится с ограничением параллельности к источникам; локальные лимитеры; идемпотентность держат уникальные индексы БД | Поиск медленнее; новый вход по OTP временно недоступен, уже вошедшие не затронуты |
| Kafka | Записи продолжаются: события копятся в outbox (алерт `OutboxBacklog`); продуктовые события сэмплируются и отбрасываются | Новые профили позже появляются в поиске, уведомления задерживаются |
| catalog | Поиск работает на read-модели и кэше карточек; профили — из кэша | Кабинет: редактирование временно недоступно |
| leads | Создание заявок недоступно; UI предлагает прямой контакт и сохраняет заявку в очередь PWA | «Заявка будет отправлена, как только сервис восстановится» |
| identity | Токены проверяются на шлюзе по закэшированному JWKS; обновление сессий и вход недоступны | Вошедшие пользователи работают до истечения access-токена |
| messaging | Чат недоступен; уведомления о заявках дублируются по SMS/email | Баннер в чате, заявки работают |
| notifications | События ждут в Kafka и доставляются после восстановления | Уведомления приходят с опозданием |
| media / Object Storage | Новые загрузки отключены; изображения отдаёт CDN из кэша | Нельзя прикрепить фото |
| trust | Очередь модерации на паузе; новые профили остаются в `pending`, новые отзывы — до проверки | Отзыв публикуется позже |
| ClickHouse | Потребитель на паузе, данные ждут в Kafka (3 дня) | Статистика кабинета отстаёт |
| Внешний SMS-провайдер | Breaker → резервный провайдер; OTP по email или push, если доступны | Код приходит другим способом |
| Одна зона | Автоматически: перезапуск подов в других зонах, failover хранилищ | Кратковременный рост задержек |

## 9. Выкладки без простоя

- **Rolling update** с `maxUnavailable: 0` и `maxSurge: 25%`. Новый под получает трафик только после readiness.
- **Readiness не проверяет общие зависимости** (БД, Kafka). Иначе их недоступность одновременно сняла бы с
  балансировки все поды сервиса. С такими сбоями работают circuit breaker и деградация. Readiness отвечает на
  вопрос «процесс готов обслуживать»: сервер слушает порт, кэши прогреты. Liveness — только «цикл событий жив».
- **Корректное завершение по SIGTERM:**
  1. readiness → false, `preStop` ждёт 5 с, пока балансировщик уберёт под;
  2. сервер перестаёт принимать новые запросы, текущие дорабатываются (gRPC `tryShutdown`, до 20 с);
  3. потребители Kafka коммитят offset и отключаются, relay outbox останавливается;
  4. пулы соединений закрываются, трейсы и метрики сбрасываются;
  5. выход в пределах `terminationGracePeriodSeconds: 30`.
- **Канареечный выпуск** (Argo Rollouts, этап 2): 5 % → 25 % → 100 % с автоматическим анализом SLO-метрик и
  откатом.
- **Флаги функций** (OpenFeature) для рискованных изменений. Включение отделено от выкладки.

## 10. Аварийное восстановление

| Сценарий | Действия | RPO | RTO |
|---|---|---|---|
| Отказ зоны | Автоматически | ≈ 0 | Минуты |
| Порча данных (ошибочная миграция, баг) | Флаг «только чтение» для домена → PITR в новый кластер на момент до инцидента → сверка → переключение | ≤ 5 мин | ≤ 1 ч |
| Потеря поискового индекса | Пересборка из `catalog.master.v1` в новый индекс, переключение алиаса | 0 | ~1 ч, поиск работает в деградированном режиме |
| Потеря региона | Развёртывание окружения Terraform-ом в резервной площадке РФ, восстановление из бэкапов, вынесенных из региона | ≤ 1 ч | ≤ 8 ч (цель этапа 3: тёплый резерв, ≤ 1 ч) |

Ранбуки лежат рядом с алертами ([observability.md](observability.md#runbooks)). Каждый сценарий отрабатывается
на учениях хотя бы раз в год.

## 11. Chaos engineering

| Эксперимент | Гипотеза | Где и как часто |
|---|---|---|
| Убийство случайных подов | Пользователь не видит ошибок (ретраи + PDB) | staging, Chaos Mesh, еженедельно |
| Задержка OpenSearch +300 мс | Открывается breaker, поиск переходит в деградированный режим, остальное не страдает | staging, ежемесячно |
| Переключение мастера PostgreSQL | Пауза записи < 30 с, без потерь, outbox догоняет | staging ежемесячно, прод раз в квартал |
| Failover шарда Redis | Задержки растут меньше чем вдвое, ошибок нет | staging, ежемесячно |
| Рестарт брокера Kafka | Продюсеры не теряют сообщений, лаг возвращается к норме | staging, ежемесячно |
| Изоляция зоны | SLO держится, автоскейлер добирает узлы в живых зонах | Game day раз в квартал |
| Отказ SMS-провайдера | Переключение на резервный, OTP доходит | staging, ежеквартально |

В проде эксперименты проводятся только при остатке бюджета ошибок > 50 % и с готовым «стоп-краном».
