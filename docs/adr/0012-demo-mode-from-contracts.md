# ADR-0012. Демо-режим и моки из контрактов (MSW)

- Статус: принято
- Дата: 2026-10-28

## Контекст

Фронтенд разрабатывается параллельно с бэкендом, а продукт нужно показывать (заказчику, мастерам на пилоте)
без поднятой инфраструктуры. Storybook и тесты нуждаются в реалистичных данных. Ручные моки быстро расходятся с
реальным API.

## Решение

- **`@masterly/mock-api`** — обработчики MSW, построенные из реестра контрактов (`on(routeName, resolver)`).
  Каждый ответ проверяется zod-схемой маршрута.
- **Данные — детерминированные фикстуры** (`@masterly/fixtures`, сидированный PRNG): 3 города, ~200 мастеров,
  цены по сегментам устройств, отзывы, встроенные дубликаты и подозрительные отзывы для демонстрации антифрода.
- **Поведение с состоянием:** заявки, ответы, диалоги, модерация и идемпотентность ведут себя как настоящий
  бэкенд в пределах процесса.
- **Один набор обработчиков везде:**
  - `API_MODE=mock` — Route Handler Next.js `/api/v1/*` отвечает из моков, сайт полностью рабочий без бэкенда;
  - Storybook — msw-storybook-addon;
  - модульные тесты.
- **`API_MODE=live`** — те же пути проксируются на шлюз (`rewrites`). Код фронтенда не меняется.

## Последствия

- **Плюсы.**
  - Фронтенд не ждёт бэкенд.
  - Демо поднимается одной командой.
  - Моки не дрейфуют: ответ, нарушающий схему, роняет тест.
  - Сквозные сценарии (заявка → ответ → выбор мастера) проверяются в e2e без инфраструктуры.
- **Минусы.**
  - Моки повторяют бизнес-правила упрощённо. Источник истины для правил — сервисы, и их поведение покрывают
    собственные тесты.
  - Нужно следить, чтобы демо-эндпоинт (`/v1/auth/demo`) был выключен в живом режиме. Это закреплено в
    конфигурации шлюза и в тесте.

## Альтернативы

- **Prism (mock-сервер из OpenAPI)** — без состояния, примеры статичны, сценарии с несколькими шагами не
  воспроизводятся.
- **Ручные JSON-фикстуры** — дрейфуют, дублируются между Storybook и тестами.
- **Общий dev-стенд вместо моков** — зависимость от его доступности и данных, конфликты между разработчиками.
