# ADR-0005. PostgreSQL 17, отдельная БД у каждого сервиса

- Статус: принято
- Дата: 2026-10-28

## Контекст

Домены (заявки, отзывы, каталог, переписка, доверие) меняются с разной скоростью и по-разному нагружены.
Общая база связала бы их схемы, релизы и отказы: долгая миграция каталога блокировала бы заявки. Нужны
транзакции и ограничения целостности (заявка и её получатели, единственный отзыв на заявку), геозапросы
(зоны выезда, филиалы) и предсказуемая эксплуатация.

## Решение

- **PostgreSQL 17** (managed, 3 хоста в трёх зонах, PITR, пулер Odyssey в transaction mode).
- **Отдельная БД и отдельный пользователь у каждого сервиса.** Доступ только к своей базе. Лёгкие домены делят
  кластер (`core`), тяжёлые (catalog, leads, messaging) получают свой.
- **PostGIS** — в catalog и trust (гео филиалов и зон выезда, близость дубликатов). **pg_trgm** — для нечёткого
  поиска в админке.
- **Схема данных:** UUIDv7, секционирование по времени через диапазоны UUIDv7, хэш-секции для матрицы цен,
  keyset-пагинация. Миграции expand → contract в Helm-хуке
  ([data.md](../architecture/data.md)).
- **Доступ из кода** — явный параметризованный SQL через тонкий слой `Db` из `@masterly/platform`
  (node-postgres в проде, PGlite в тестах), без ORM. Схема живёт в SQL-миграциях: секционирование по UUIDv7,
  частичные и покрывающие индексы ORM всё равно не выразит. Запросы видны при ревью и в `pg_stat_statements`
  такими, какими их написали. Каждый репозиторий покрыт тестами на настоящем PostgreSQL (PGlite).

## Последствия

- **Плюсы.**
  - Независимые релизы и миграции.
  - Изоляция отказов и блокировок.
  - Простые ACID-транзакции внутри домена.
  - Зрелые инструменты (EXPLAIN, `pg_stat_statements`, PITR).
- **Минусы.**
  - Нет JOIN между доменами: нужные данные приходят событиями и хранятся локально как read-модель.
  - Больше баз в эксплуатации, но это закрывает managed-сервис.
  - Вертикальный предел одного мастера: при > 5 000 TPS записи понадобится шардирование
    ([capacity-planning.md](../architecture/capacity-planning.md#8-когда-и-что-масштабировать-дальше)).

## Альтернативы

- **Общая БД** — быстрее на старте, но связывает всё со всем.
- **MongoDB** — гибкие документы, но слабее с транзакциями между коллекциями и с ограничениями целостности,
  которые нужны для заявок и отзывов.
- **Распределённые SQL (YDB, Citus)** — кандидаты для шардирования leads и messaging, когда рост этого
  потребует. Сейчас это преждевременная сложность.
