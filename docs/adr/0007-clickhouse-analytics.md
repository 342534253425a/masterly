# ADR-0007. ClickHouse для продуктовой аналитики

- Статус: принято
- Дата: 2026-10-28

## Контекст

Требования к аналитике:
- мастерам — показы в поиске, просмотры, клики по контактам, заявки, конверсии и поисковые запросы, которые
  привели к профилю;
- платформе — запросы без результатов, популярные категории, средние цены по городам, скорость ответа мастеров.

Это сотни миллионов событий в сутки и агрегатные запросы по месяцам. Сторонние счётчики противоречат требованию
«без скрытого трекинга» и отдают данные третьей стороне.

## Решение

- **ClickHouse** (managed, 3 шарда × 2 реплики). Потребитель analytics пишет из Kafka батчами.
- **Сырые таблицы** `events` и `searches`. В `searches` одна строка на выдачу, показы карточек хранятся массивом.
  Это на порядок меньше строк, чем событие на каждую карточку.
- **Материализованные представления** считают `master_daily` (отчёт мастера) и `search_gaps_daily` (расширение
  каталога по спросу).
- **Хранение:** горячие 30 дней на SSD, старше — в Object Storage (TTL MOVE). Сырые данные удаляются через
  90–180 дней, агрегаты хранятся бессрочно.
- **Приватность:** только псевдонимный `user_hash`, события только при согласии. При отзыве согласия данные
  пользователя удаляются.

## Последствия

- **Плюсы.**
  - Отчёты за секунды на миллиардах строк, дешёвое хранение за счёт сжатия колонок.
  - Собственные данные без передачи третьим лицам.
  - SQL доступен аналитикам напрямую (Grafana, DataLens).
- **Минусы.**
  - Не транзакционная БД: точечные обновления дороги, удаление по пользователю — мутациями пакетно раз в сутки.
  - Нужна дисциплина схем: сортировочный ключ и партиции выбираются под запросы.

## Альтернативы

- **PostgreSQL** — не для сотен миллионов строк в сутки с агрегатами по месяцам.
- **Сторонние веб-счётчики** — передача данных третьей стороне, скрытый трекинг, нет данных на уровне мастера.
- **Хранилища вне РФ** — недопустимы по 152-ФЗ.
