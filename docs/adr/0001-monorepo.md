# ADR-0001. Монорепозиторий на pnpm и Turborepo

- Статус: принято
- Дата: 2026-10-28

## Контекст

Фронтенд, шлюз и десять сервисов используют общие контракты, доменное ядро (классификатор проблем, гео,
SimHash), фикстуры и proto-схемы. Если вести их в отдельных репозиториях, любое изменение контракта превращается
в цепочку версий и синхронных релизов. Сборка и тесты при этом должны оставаться быстрыми, несмотря на
десятки пакетов.

## Решение

- Один репозиторий: `apps/*` (web, gateway), `services/*` (доменные сервисы), `packages/*` (contracts, kernel,
  fixtures, proto, mock-api, platform).
- **pnpm workspaces** со строгой изоляцией зависимостей. Версии общих библиотек задаются в **catalog** в
  `pnpm-workspace.yaml`, у всех пакетов одна версия zod, TypeScript и NestJS. Скрипты установки зависимостей
  разрешены точечно через `allowBuilds`.
- **Turborepo** строит граф задач (`generate → build → typecheck/test`), кэширует результаты и в CI запускает
  только затронутое (`--affected`).
- Образы сервисов собираются из одного Dockerfile: `turbo prune` → установка → сборка → `pnpm deploy --prod`
  → distroless.

## Последствия

- **Плюсы.**
  - Изменение контракта и всех его потребителей — один PR, а несовместимость ловит `tsc`.
  - Единые линтеры, версии и CI.
  - Атомарный рефакторинг через границы сервисов.
- **Минусы.**
  - Репозиторий растёт.
  - Нужна дисциплина границ: сервис не импортирует код другого сервиса, только `packages/*`.
  - CI должен уметь собирать затронутое, иначе время сборки растёт линейно.
- **Владение.** Деплой независим, каждый сервис выкатывается своим образом и Helm-релизом. Монорепозиторий не
  означает монолитный релиз.

## Альтернативы

- **Polyrepo + npm-пакеты контрактов.** Версионирование и согласованные релизы обходятся дороже, чем кажется,
  а дрейф контрактов обнаруживается в рантайме.
- **Nx.** Мощнее в генераторах, но тяжелее и навязывает свою модель плагинов. Turborepo проще и быстрее для
  графа задач на pnpm.
- **Bazel.** Герметичные сборки, но для TypeScript-стека несоразмерная стоимость поддержки.
