# ADR-0002. Feature-Sliced Design во фронтенде

- Статус: принято
- Дата: 2026-10-28

## Контекст

Во фронтенде десятки экранов для трёх ролей (клиент, мастер, администратор), общие сущности (мастер, услуга,
заявка) и сценарии (поиск, сравнение, заявка, раскрытие контактов). Без явных правил зависимостей такой код
быстро превращается в клубок, где изменение карточки мастера ломает кабинет.

## Решение

- Код приложения лежит в `src/` по слоям FSD: `app → pages → widgets → features → entities → shared`.
  Импорт разрешён только вниз по слоям и только через публичный API слайса (`index.ts`).
- Корневая папка `app/` Next.js содержит только маршрутизацию: файлы маршрутов импортируют страницы из
  `src/pages`. Пустая корневая `pages/` с README не даёт Next.js принять `src/pages` за Pages Router.
- Серверное и клиентское разделены явно: `shared/api/server.ts` (`server-only`) и браузерный `apiCall`.
- Правила проверяет **Steiger** в CI. Компоненты документируются в **Storybook**: истории живут рядом с
  компонентами, данные приходят из MSW-моков ([ADR-0012](0012-demo-mode-from-contracts.md)).

## Последствия

- **Плюсы.** Предсказуемое место для любого кода, изолированные фичи, понятная зона ответственности при ревью.
  Сущности (`entities/master`) переиспользуются в поиске, сравнении, избранном и кабинете.
- **Минусы.** Порог входа: новым разработчикам нужно освоить методологию. Иногда соблазн «пробросить»
  импорт вверх. Это ловит линтер.

## Альтернативы

- **Папки по фичам без правил** — работает до первого десятка фич.
- **Atomic Design** описывает только UI, а не бизнес-логику и данные.
- **Микрофронтенды** дают независимые релизы команд ценой согласованности UX и производительности.
  Преждевременно, пока одна команда.
