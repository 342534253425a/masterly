# ADR-0004. Kafka как шина событий, transactional outbox и inbox

- Статус: принято
- Дата: 2026-10-28

## Контекст

У заявки много побочных эффектов в чужих доменах: уведомить мастеров с учётом тихих часов, открыть диалоги,
обновить воронку, дать право на отзыв. Профиль мастера должен попадать в поисковый индекс и проверку на
дубликаты. Синхронные цепочки вызовов связали бы доступность всех сервисов: заявка падала бы, если лежат
уведомления. Нужно надёжно доставлять события, переигрывать их при пересборке read-моделей и масштабировать
потребителей независимо.

## Решение

- **Kafka** (managed, KRaft, RF = 3, `min.insync.replicas = 2`) — шина доменных событий. Топики версионируются
  (`leads.lead.v1`), ключ — id агрегата.
- **Transactional outbox** у каждого производителя. Событие пишется в таблицу `outbox` в той же транзакции, что и
  данные. Relay публикует его с `acks=all` и сохраняет порядок внутри агрегата (шард outbox обрабатывает
  один relay).
- **Inbox** у каждого потребителя: `(consumer, event_id)` в той же транзакции, что и эффект. Повторы безопасны.
- **Повторы:** в процессе с jitter, затем `<topic>.retry`, затем `<topic>.dlq` с алертом и инструментом
  переигрывания.
- **Компактированные топики-снимки** (`catalog.master.v1`, `reviews.rating.v1`) для event-carried state
  transfer: read-модели пересобираются чтением топика с начала.
- **Масштабирование потребителей по лагу** через KEDA.
- Отложенные задачи с точным временем (тихие часы) — **строки с `scheduled_for` в БД сервиса**, разбор через
  `FOR UPDATE SKIP LOCKED`, а не Kafka: точное время, переживает рестарты, без отдельного брокера задач.

Подробности — [events.md](../architecture/events.md).

## Последствия

- **Плюсы.**
  - Сервисы развязаны по времени и доступности: заявка создаётся, даже если уведомления лежат.
  - Есть повторное чтение и пересборка индексов.
  - Естественная точка для аналитики.
  - Порядок событий агрегата гарантирован.
- **Минусы.**
  - Согласованность в конечном счёте: UI должен это учитывать (оптимистичные обновления, «появится в поиске
    в течение минуты»).
  - Нужны дисциплина идемпотентности и наблюдаемость лагов.
  - Операционная сложность Kafka (снята managed-сервисом).

## Альтернативы

- **RabbitMQ.** Отличен для очередей задач, но нет повторного чтения, компактирования и партиционированного
  порядка. Для отложенных задач хватило таблицы и SKIP LOCKED в PostgreSQL.
- **NATS JetStream.** Лёгкий и быстрый, но нет managed-варианта в выбранном облаке, экосистема коннекторов меньше.
- **Redis Streams.** Ограничения по объёму и долговечности, нет компактирования.
- **CDC (Debezium / Data Transfer) вместо outbox-поллера.** Меньше задержка, но нужны слоты логической репликации
  в managed-PG и есть риск роста WAL. Оставлено как оптимизация на будущее.
- **Синхронные вызовы и вебхуки** — каскадные отказы и связность по доступности.
