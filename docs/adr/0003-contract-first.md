# ADR-0003. Contract-first: zod-реестр для REST, Protobuf для gRPC и событий

- Статус: принято
- Дата: 2026-10-28

## Контекст

Внешний API нужен вебу, PWA, в будущем мобильным приложениям и, возможно, партнёрам. Внутри десять сервисов
вызывают друг друга и обмениваются событиями. Дрейф между тем, что ожидает клиент, и тем, что отдаёт сервер, —
главный источник интеграционных багов. Ещё нужны моки для разработки фронтенда раньше бэкенда.

## Решение

- **Внешний REST — zod-реестр маршрутов** в `@masterly/contracts`. Каждый маршрут описывает метод, путь,
  параметры, тело, ответ, уровень доступа, подсказку кэширования, лимит запросов и признак идемпотентности.
  Из реестра выводятся:
  - типизированный клиент (`RouteInput` / `RouteResponse`) для web;
  - OpenAPI 3.1 (`z.toJSONSchema`) для документации и партнёров;
  - маршруты шлюза: валидация входа, RBAC, лимиты;
  - MSW-моки с проверкой ответов по схеме.
- **Внутренние вызовы — gRPC с Protobuf** (Buf v2). События Kafka — тоже Protobuf. Типы TypeScript
  генерирует ts-proto, на рантайме работает `@grpc/proto-loader`.
- **Совместимость в CI:**
  - `buf lint`;
  - `buf breaking` против `main`;
  - снимок OpenAPI с проверкой несовместимых изменений;
  - тесты контрактов в `@masterly/contracts`.

## Последствия

- **Плюсы.**
  - Одна схема и для валидации, и для типов, и для документации, и для моков. Рассинхронизация ловится
    компилятором, а не пользователем.
  - Protobuf компактен и строго версионируется, что важно для 25k RPS внутри и долгоживущих топиков.
- **Минусы.**
  - Две системы схем (zod снаружи, proto внутри). Маппинг между ними делает шлюз, и его покрывают тесты.
  - Изменения в proto требуют дисциплины: только добавление полей.

## Альтернативы

- **GraphQL (federation).** Гибкие выборки, но сложнее кэширование на CDN, есть N+1 и стоимость запросов, нужен
  отдельный слой схем. Наши экраны хорошо ложатся на BFF-маршруты.
- **tRPC.** Замечательно внутри TS-монорепозитория, но нет стабильного OpenAPI для внешних клиентов, и протокол
  привязан к TS.
- **OpenAPI-first (YAML).** Генерация кода в обе стороны, но менее эргономично, чем zod, и нет единой схемы для
  рантайм-валидации.
- **gRPC-Web до браузера.** Теряется HTTP-кэширование, CDN и простота отладки, SSR сложнее.
